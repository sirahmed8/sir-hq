### Item r15-3: the republish helper did not keep the four files truthful

Cause: `plans/generate_dashboard.py` had been reduced to a shim that writes only
`ops/artifact/control-room.html`. Nothing wrote `ops/dashboard.html` (last write 13:13),
`ops/public/dashboard.html` (15:12) or `ops/artifact/CHANGED.txt` (15:12). The local server served
the stale 345 KB page while the artifact was 65 KB. Two more lies sat next to them:

- `scripts/publish_artifact.py` counted a publish as successful when the reply contained the word
  `published`, and the failed run of 17:05 replied `Not published: the Artifact tool is not
  available in this session`, so `ops/artifact/PUBLISHED.txt` recorded a hash that was never
  published.
- `scripts/refresh-control-room.py` compared the two state files as whole strings
  (`"2026-11-12 17:05 1d85107f"` against `"1d85107f"`), so it could never report "IN SYNC".

Changes:

- `plans/generate_dashboard.py` now writes the page and both mirrors byte for byte
  (`ops/artifact/control-room.html`, `ops/dashboard.html`, `ops/public/dashboard.html`) and the
  content hash into `ops/artifact/CHANGED.txt`. The privacy fence (`plans/dashboard_privacy.py`)
  now runs on the rendered page before anything is written.
- `scripts/publish_artifact.py` only records a hash when the reply starts with `published`; failures
  are logged as `FAILED <hash>: <reply>` and leave `ops/artifact/PUBLISHED.txt` untouched. The
  state file holds one hash per line (the time lives in `ops/artifact/publish.log`).
- `scripts/refresh-control-room.py` compares the hashes by value and checks the mirrors against the
  artifact, so its log line is true.
- `ops/artifact/PUBLISHED.txt` was corrected to `20ee1159`, the last hash that was really published
  (the 17:05 value came from the failed publish).
