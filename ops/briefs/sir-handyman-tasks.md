## M0: Foundations and kit setup

1. Monorepo scaffold with tokens, RTL, the health route and CI. Create the monorepo skeleton under `D:/Projects/SIR Handyman` (apps/web with route groups `(customer)`, `(worker)` and `/owner`, apps/api, packages/core, packages/data, packages/ui, packages/kit, apps/mobile, apps/desktop, docs, scripts) with strict TypeScript, Tailwind v4 tokens, RTL-first styles, an `/api/health` route returning JSON, and a `pnpm verify` script that runs typecheck, lint, tests, build and gitleaks. No UI beyond the health route and a placeholder home page with the five states. Exit check: `pnpm verify` runs and the output was seen green, and the health route answers on both hosts later.

2. The product's own Firebase project and the `owner-auth` package with negative tests. Verify whether a Firebase project and a GitHub repo named `sir-handyman` already exist; if not, create the Firebase project `sir-handyman` on the free Spark plan and the GitHub repo `sirahmed8/sir-handyman` (private) as the only remote. Implement `owner-auth` (Google sign-in via Firebase Auth, ID token verified on the server with JWKS, allow-list for owner and admin, HttpOnly Secure SameSite=Strict cookie, phone OTP as worker second factor, rate limits) with negative tests: forged token returns 403, client-side flag flip grants nothing, non-owner token on `/owner` returns 403, non-worker token on `/worker` returns 403. Exit check: the tests pass and the Firebase project and repo names are written in the project checkpoint.

3. The data model (`packages/core`) and the Firestore rules, with emulator tests. Implement the domain types and zod schemas from the plan section 5.3 (User, WorkerProfile, WorkerVerification, ServiceCategory, JobRequest, Quote, Booking, JobMessage, Rating, Wallet, WalletEntry, Payout, Dispute, PlatformFee, SafetyFlag) and the Firestore repositories in `packages/data`, one interface per entity, with deny-by-default rules and per-user and per-role claims. Emulator tests must include a cross-tenant read that fails and a cross-role write that fails. Exit check: the emulator rules tests pass, including the cross-tenant read that must fail.

4. The service taxonomy and the worker application flow with phone OTP and safety-QA. Implement the own taxonomy (plumbing, electricity, carpentry, painting, AC, cleaning, pest control, appliances, alumetal, gas water heaters, moving) with an ar/en slug and a safety tier (standard / gas_electrical) on each category; the worker application flow (categories, photo, bio, service area as a geo hash, phone OTP, safety-QA questionnaire for gas/electrical); and the KYC pass/fail flag integration in sandbox mode (provider chosen in M0, never a document image stored). Exit check: a worker can apply and reach "in review", a forged client-side "verified" flag gives nothing (server reads only the KYC flag), and the safety-QA questionnaire blocks a gas job assignment to a worker without the pass, with a test.

5. The request flow with photos, GPS/pin and time window. Implement the customer request flow: pick a category, describe the job in one line plus messy text, attach size- and type-checked photos with signed URLs, drop a GPS pin or enter an area, pick a time window, review and post. The request shows the five states on every screen and the empty catalog area shows an empty state with one action. Exit check: a photo of the wrong type or over size is refused before upload, the request is created with a geo hash and never a street address in the public payload, and Playwright covers the request flow at 390 px and 1280 px, Arabic and English, light and dark.

## M2: Request, quote and acceptance under contention

6. The worker quote feed, the quote comparison screen and the accept transaction. Implement the nearby-worker quote feed (service area + radius, verified only, filters by category), the quote comparison screen (price, worker rating, jobs completed, distance, ETA), and the accept transaction with an idempotency key: verify quote pending and request open, create the booking with a hashed visit code, move the quoted amount into wallet escrow as a `hold` entry, notify both parties. Exit check: 20 parallel accepts of different quotes on one request produce exactly one booking and 19 clean rejections (emulator), a quote from a worker outside the service area is refused, and the agreed price cannot change without both-side consent, with a test.

7. En-route tracking, the visit code and the in-app chat. Implement the ephemeral en-route location pings (24h TTL, then deleted; the booking stores only arrivedAt), the 4-digit visit code (hashed at rest, shown to the customer at acceptance, required for the worker to mark arrival, wrong code fails and correct code moves the booking to `arrived`), and the in-app chat (text + photos + system messages for every state transition, tied to the booking). Exit check: a wrong visit code is rejected and a correct one advances the booking, en-route pings older than 24h are deleted by the nightly job, and Playwright covers the en-route and arrival screens in Arabic and English.

8. Escrow release, Paymob/Fawry webhook (test mode) and the wallet ledger. Implement the escrow flow: customer confirms completion, then `release` minus fee plus worker credit; or 72h passes after in_progress and the hold auto-releases (time-travel tests in the emulator); Paymob and Fawry in test mode with HMAC-SHA256 signed webhooks verified server-side, ten negative tests (tampered, replayed, unsigned, wrong timestamp, wrong amount), and the append-only wallet ledger with idempotency keys on every movement. Exit check: the ten negative webhook tests pass, no `dev_signature` or any bypass exists in the code, and escrow release and auto-release both pass in the emulator with time travel.

9. The ratings system (completed jobs only) and share-visit with a trusted contact. Implement ratings: one rating per (booking, rater), written only when the booking status is completed, locked after the dispute window closes, rated side sees the aggregate only after one rating exists; share-visit: a one-tap link for a trusted contact showing the worker's name, photo, ETA and visit-code status, read-only, expiring when the booking completes. Exit check: a rating without a completed booking is refused by the server with a test, a second rating by the same user on the same booking is refused, and the share-visit link shows the read-only page and expires on completion, with a test.

10. The owner-only analytics page and the dispute queue. Implement `/owner` with server-verified owner token and 403 for everyone else: real metrics only (customers and workers DAU/WAU/MAU, open requests, quotes per request, time-to-accept, completion rate, dispute rate, agreed price per category, platform fee revenue EGP, payout queue, worker funnel, ratings distribution, safety flags, AI cost, error rate, per-city density) read from aggregates; the dispute queue with evidence photos and both sides' messages; the safety-flag queue; the worker verification queue; the dispute summary AI (advisory only, quotes real messages). Exit check: a non-owner token gets 403, a forged token gets 403, empty metrics show a dash and the reason, never a zero dressed as a fact, and Playwright covers the /owner page in Arabic and English.
