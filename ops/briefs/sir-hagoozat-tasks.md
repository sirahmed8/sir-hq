## T5. The slot lock and the booking transaction

Build the booking core in `packages/data` and `packages/core`: a slot document with a status and a hold expiry, a Firestore transaction that books a slot with an idempotency key, a 15 minute hold that releases itself, and a clean rejection for every loser of the race. The rule that matters: 20 parallel requests for one slot produce exactly one booking and 19 clean rejections, and a hold that expires makes the slot bookable again. No `dev_signature` and no bypass flag of any kind exists in the code, because the legacy `dev_signature` fallback in the subscription webhook let anyone activate a tier. Exit check: the parallel test runs and its real output is in the report, plus a test that shows the hold expiring. Report: the transaction code path in words, the test output, and the measured time the hold lasts.

## T9. The squad balancer as a pure function, and the fairness meter

Build the balancer in `packages/core` with no AI in the decision and no I/O: it takes a list of players with their positions and ratings and returns two balanced teams plus the reason for the split in plain words. The signature interaction is the fairness meter: drag a player from one team to the other and the meter settles with a spring, so the balance is felt before it is read. Add a property test that the rating-sum difference between the two teams stays inside the stated bound, and a test that the same input always produces the same teams, because a random split would be unfair and unreadable. The AI explanation comes later in M5 and only writes the sentence. Exit check: the property test output is in the report and the meter is demonstrated on screen with a before and after screenshot. Report: the balancing rule in plain words, the bound the test enforces, and the measured worst-case difference.
