# First ten build tasks for SIR Cars (round r54, HQ)

Ready to queue for the free agents. Each task is one paragraph; the agent reads the plan `D:/Projects/_SIR/plans/sir-cars.md` and the competitor study `D:/Projects/_SIR/ops/competitors/sir-cars.md` first, then does only this task, runs the checks, commits, pushes and ticks the checklist.

1. Monorepo scaffold with tokens, RTL, the health route and CI. Create the monorepo skeleton under `D:/Projects/SIR Cars` (apps/web, apps/api, packages/core, packages/data, packages/ui, packages/kit, apps/mobile, apps/desktop, docs, scripts) with strict TypeScript, Tailwind v4 tokens, RTL-first styles, an `/api/health` route returning JSON, and a `pnpm verify` script that runs typecheck, lint, tests, build and gitleaks. No UI beyond the health route and a placeholder home page with the five states. Exit check: `pnpm verify` runs and the output was seen green, and the health route answers on both hosts later.

2. The product's own Firebase project and the `owner-auth` package with negative tests. Verify whether a Firebase project and a GitHub repo named `sir-cars` already exist; if not, create the Firebase project `sir-cars` on the free Spark plan and the GitHub repo `sirahmed8/sir-cars` (private) as the only remote. Implement `owner-auth` (Google sign-in via Firebase Auth, ID token verified on the server with JWKS, allow-list for owner and admin, HttpOnly Secure SameSite=Strict cookie, rate limits, second factor offer) with negative tests: forged token returns 403, client-side flag flip grants nothing, non-owner token on `/owner` returns 403. Exit check: the tests pass and the Firebase project and repo names are written in the project checkpoint.

3. The data model and the Firestore rules, with emulator tests. Implement the domain types and zod schemas in `packages/core` (Car, Trim, PriceEstimate, Specs, Listing, FuelEntry, MaintenanceEntry, Reminder, Workshop, Part, Review, User) and the Firestore repositories in `packages/data`, one interface per entity, with deny-by-default rules and per-user and per-listing-owner claims. Emulator tests must include a cross-tenant read that fails. Exit check: the emulator rules tests pass, including the cross-tenant read that must fail.

4. The price-estimate engine with a cited source and range. Implement the price-estimate engine that reads trim price lists and submitted listings and returns a range plus the source and its last-checked date. Every estimate shown on screen must display its source and range; a stale source is flagged, never silently used. Exit check: a price estimate for a known trim returns a range and a source, and the source is shown on screen, with an automated test.

5. The specs comparison view with highlight of differences. Implement the specs comparison of two or three cars side by side, with the differences highlighted, at 390 px and 1280 px, in Arabic and English, in light and dark, with the five states. Exit check: the comparison renders correctly in all four combinations and a Playwright test covers the happy path.

6. The listing creation flow with photos and phone verification. Implement the listing model, the creation flow with photos, trim, year, mileage, city and price, phone verification by OTP before publish, and size- and type-checked photo uploads with signed URLs. Exit check: a listing cannot be published without phone verification (e2e test blocked), a wrong-type or too-large photo is refused, and a stored photo is reachable only with a valid signed URL.

7. The listing page, the contact flow and the consent disclosure screen. Implement the listing page with the inspection badge and the report-a-listing flow, the contact flow that hides the seller's phone until a declared-interest tap, and the consent disclosure screen shown before the phone is revealed. Exit check: the buyer's phone is hidden until the declared-interest tap and the consent screen is shown before the seller's phone is revealed, with an e2e test.

8. The car record, the fuel log and the maintenance log. Implement the car record (one record per car, reused across listings, fuel, maintenance and reminders), the fuel log with consumption and cost per kilometre, and the maintenance log with service intervals and reminders. Exit check: a user can add a car, log fuel and maintenance, and see consumption and cost per kilometre computed from real entries, with a test.

9. The licence, insurance and service reminders with the cost-of-ownership dashboard. Implement the licence, insurance and periodic inspection reminders that fire at a round hour through the Telegram sender, plus the cost-of-ownership dashboard (fuel, maintenance, insurance, tax, fees) and the weekly Telegram report with numbers and their meaning. Exit check: a reminder fires at a round hour and the weekly report arrives with the numbers and their meaning, with a test.

10. The owner-only analytics page and the billing fallback page. Implement `/owner` with server-verified owner token and 403 for everyone else, showing real metrics only (users, listings, contacts, price-estimate calls, AI cost, error rate, workshops, parts, subscriptions, revenue), and the billing fallback page with "Subscriptions launching soon" and an email capture that creates a lead document and rejects an invalid address. Exit check: a non-owner token on `/owner` gets 403, a forged token gets 403, the pricing page shows the test prices with auto-detected currency, and the email capture creates a lead document and rejects an invalid address.
