## T6. The Java discovery, the JVM argument compiler and the options.txt writer

Build the three pieces the launcher needs before it can start the game, in `packages/engine` with unit tests. The Java discovery reads the PE header of each candidate executable to learn its architecture, probes both HKLM and HKCU on Windows, scans the common install locations, parses the version with semver rules, and reports the runtime that fits the Minecraft version the pack needs. The JVM argument compiler takes the machine's real physical memory and produces the memory and garbage-collection arguments for the chosen profile (Balanced, Performance, Ultra), explains each argument in one plain sentence, and never allocates more than the machine can give without starving the operating system. The options.txt writer enforces the two house invariants from the legacy code: modern profiles use GLFW key names only (`key.keyboard.*`, `key.mouse.*`) and never numeric keycodes, ported from `development/launcher_core/controls_service.py` which carries the bidirectional GLFW-token to LWJGL2-scancode table, and the launch-time sanitizer forces `fullscreen:false`, `exclusiveFullscreen:false` and `overrideWidth:0` before the game starts, ported from `_sanitize_launch_environment` in `development/launcher_core/native_runner.py`, which exists to kill the hybrid-graphics DWM deadlock, the exclusive-fullscreen lockout and the black screen on launch and exit. Exit check: the discovery finds the runtimes installed on this machine and the output is pasted in, the compiler is tested across 4 GB, 8 GB, 16 GB and 32 GB machines and the chosen arguments are printed for each, and the writer test proves that a numeric keycode is rejected. Report: the discovery sources, the argument table per profile, the invariant list, and what a player reads when no suitable Java is found.

## T7. The crash-log parser and the plain-language finding

Build the crash analyser in `packages/engine` as pure deterministic code, with no AI inside it. It reads a Java crash report, a native `hs_err_pid*.log`, an OutOfMemory report of any variant, a Mixin injection failure, a missing or mismatched dependency, a corrupted region file and a shader compilation error, and returns a structured finding: the category, the offending mod or file if there is one, the evidence line, and a suggested action. Port the coverage from the legacy `crash_analyzer_service.py`, which already handled Mixin conflicts, Java version mismatches, the OutOfMemory spectrum, native crash logs, dependency conflicts, corrupted region files and shader compilation failures. The rule that matters: when no mod is at fault, the finding says so. It never guesses a culprit. The Arabic and English sentence is written later by the AI layer (T-M5 task), so the parser returns the finding and a template key, never a fabricated sentence. Exit check: the parser is tested against 20 real-shaped crash logs in Arabic and English input, the category and the named mod are correct in every case, and the "no mod is at fault" case returns exactly that with the test output pasted in. Report: the supported categories, the finding schema, the twenty test logs, and the one case where the parser is allowed to be unsure.

## T10. The server manager: start, stop, logs, world backup and a proven restore

Build the server manager in `packages/engine` and its screens in `packages/ui`: it starts and stops a server process, tails the log live, shows the real TPS and RAM from the server's own output, and takes a world backup on a schedule and on demand. The backup is a rolling archive of the world folder, the restore is the operation that matters: it restores into a clean folder and then compares the file hashes of the restored world against the original, so a restore that only "ran without an error" is never called a success. The server binds to localhost by default and warns before it opens a port to the network. Port the legacy coverage from `server_core` (persistent lifecycle configuration, automated world snapshots, live TPS and RAM) and from `worlds_service.py` (world saves, thumbnails, backups, folder operations). Exit check: the test server starts and its log lines appear in the tail, it stops cleanly and the port is closed afterwards, a backup restores and the hash comparison is printed with the file count that matched, and the localhost default is proven by a test that shows the binding address. Report: the server lifecycle path in words, the backup format and retention, the hash comparison output, and the exact warning the player sees before a port is opened.
