2. **The data source ledger and the source probes.** Write `docs/DATA_SOURCES.md` with one row per candidate source: Steam store endpoint, Steam Web API with a key, Epic Games Store free game promotions, GOG product API, Xbox and PlayStation, the public giveaway APIs (FreeToGame, GamerPower), the key shop and retailer affiliate programmes, and the Egyptian shops. Each row carries the URL, the terms status (cleared, needs a partner agreement, or blocked), the last-checked date, the trust tier we would assign it, and what it may be used for. Add a repeatable probe script under `scripts/` that records the response of each cleared source with the date, so the ledger can be refreshed. Use the findings already measured on 2026-11-12: the Steam public store endpoint answers a country code and returns `$39.99 USD` for Elden Ring with `cc=EG`, `249.00 SR` for `cc=SA` and `249.00 AED` for `cc=AE`, so Steam has no Egyptian pound price; the old free Steam app-list method answers "Method 'GetAppList' not found in interface 'ISteamApps'"; GG.deals and SteamDB answer automated requests with a bot challenge and must never be treated as a feed; the FreeToGame API answers a JSON list. Do not scrape anything whose terms forbid it, and do not copy a community price database. Exit check: the ledger exists with a dated terms status for every row, the probe script runs and its output is pasted into the report, and no source is marked cleared without a line of evidence.

3. **The monorepo scaffold, the design tokens, the RTL shell and CI.** Create the monorepo skeleton (`apps/web`, `apps/api`, `packages/core`, `packages/data`, `packages/ui`, `packages/kit`, `apps/mobile`, `apps/desktop`, `docs`, `scripts`) with strict TypeScript, Tailwind v4 tokens, absolute imports, layers depending inward only, files under 300 lines and no `any`. Seed the design tokens from `plans/sir-game-deals.md` section 6: the deep teal seed colour, the second accent reserved for the lowest-ever flag, light, dark, system and high-contrast themes, logical CSS properties only, an RTL-first Arabic stylesheet with a proper Arabic face, 44 px touch targets and the five states on every view. Add an `/api/health` route that returns real status values and never a fake one, a root `verify` script, and the GitHub Actions workflow on `main`. No product screen beyond the shell and a home placeholder that carries the five states honestly. Exit check: `pnpm verify` output is green, the health route answers with real values, and the placeholder is screenshotted in Arabic and English at 390 px and 1280 px in light and dark inside `.sir/evidence/`. Report: the tree, the token file, the commands with their real output, and anything that could not be installed for free.

4. **The product's own Firebase project and the `owner-auth` package with negative tests.** Build `packages/kit/owner-auth`: Google sign-in through Firebase Auth on the `sir-game-deals` project, server-side ID token verification with JWKS, an owner and admin allow-list that fails closed, the web session in an HttpOnly, Secure, SameSite=Strict cookie with no token in localStorage, rate limits on sign-in, and a second factor offer for owner accounts. Write the negative tests: a forged token gets 403, a client-side flag flip grants nothing, a non-owner token on `/owner` gets 403, and a revoked session cannot write. Exit check: the three negative tests run and fail in the expected way, owner sign-in works in the browser on screen, and no key is printed or committed. Report: the project id, the commands with their real output, the ignored keys path, and the note that the Gemini and OpenRouter keys for this product will live on this product's own accounts only.

5. **The data model, the Firestore rules and the emulator tests.** Implement the domain types and zod schemas in `packages/core` (Game, Store, Offer, PricePoint, PriceHistory, Giveaway, WatchItem, Alert, User, Subscription) and the Firestore repositories in `packages/data`, one interface per entity, exactly as the collections table in `plans/sir-game-deals.md` section 5.5 describes. Every price is an integer in the smallest currency unit; every converted number carries the rate and the observation time; `pricePoints` is append only; the derived `priceHistory` holds the lowest ever with its store and date. The rules deny by default, check `request.auth` on every read and write, scope `watchlists`, `alerts`, `wishlistImports`, `notifications` and `giveawayClaims` to their owner, keep `subscriptions` and `leads` server-only, and let the public read collections carry no personal data. Document every collection with its fields, indexes and access rules in `docs/data-model.md`. Emulator tests must include a cross-user read that fails and an unauthenticated write that fails. Exit check: the emulator tests pass with real output in the report, the rules compile with no warning, and the document lists every rule stricter than the obvious default.

6. **The scheduled ingestion pipeline, the price history engine and the lowest-ever calculation.** Build the ingestion job for the sources cleared in task 2: it runs on a schedule at a round time, writes an `ingestionRuns` record with the item counts and the errors, is idempotent on the same observation, and never overwrites a price point. Build the history engine that appends `pricePoints`, computes the lowest ever with its store and its date, computes the thirty day average, and produces the downsampled curve for the chart. A new lowest price is one transaction (write the point, then update the derived history) so two stores dropping in the same minute cannot produce two lowest-ever flags. Build the freshness rule (two days) and the currency conversion that stores the rate, its source and its observation time in `fxRates`. Exit check: a live run against at least two cleared sources produces real price points, a game observed at two prices shows two real points and one correct lowest-ever flag, a stale price is flagged, and the report shows the run record and the rate used with its date.

7. **The deals feed, the game detail page with the history curve, and the five states.** Build the first real product screens in `apps/web`: the deals feed with the filters (store, platform, genre, discount depth, price range, DRM free, region, activation type) and the sorts (discount, absolute saving in the visitor's currency, lowest ever), the game detail page with the price curve, the lowest-ever flag naming its store and date, and every store offer showing its region, its activation type and its trust tier, and the free game list with the end time. Every price on screen shows the visitor's currency, the original currency, the rate used and the moment it was seen. Implement idle, loading skeleton, empty with exactly one action, error with retry and populated on every view, with skeletons matching the final geometry and no fake data anywhere. Exit check: Playwright screenshots at 320, 390, 768, 1280 and 1920 px in Arabic and English in light and dark, all in `.sir/evidence/`, with no horizontal overflow and no clipped text, and a check that no placeholder price, game or discount exists in the built bundle.

8. **The watchlist, the Steam wishlist import, the alert engine and the Telegram bot link.** Build the watchlist with a target price in the user's currency, the Steam wishlist import from the user's own account (the token is stored server-side and encrypted, never in localStorage, and deleted on unlink; it never reads another user's account), and the alert engine with the four types (price below, any discount, giveaway start, giveaway ending), quiet hours, the rate limits and a de-duplication window so one offer never fires twice. Add the Telegram bot link following `plans/BOT_ARCHITECTURE.md`: one bot for the product, each user links their own account, with the five states (not linked, linking, linked, syncing, failed with retry); a wrong chat id is ignored and an unapproved destructive command is refused. Exit check: the import brings real items onto the watchlist, a crossing price sends exactly one alert inside the window and none on a repeat, quiet hours suppress a non-critical alert, the free tier limits (5 watchlist items, 10 alerts) are enforced on the server, and the tests for all of this pass with real output.

9. **The free game tracker, the countdown and the claim reminder.** Build the giveaway ingestion from the cleared free game sources, the free game page with the claim link, the end time, the region eligibility and the countdown, and the claim reminder that fires before the window closes exactly once per giveaway. A giveaway that is no longer visible is marked unverified rather than hidden, and the countdown reaches zero and then marks the offer as ended instead of counting below zero. Build the reminder delivery through the shared Telegram sender and record every delivery in `notifications` so the owner page can show the truth. Exit check: the free game list shows real giveaways with a real end time, the reminder is sent once and recorded, the countdown behaviour is covered by a test, and the screenshots show the empty and the error states as honestly as the populated one.

10. **The owner analytics page with the source health panel, the pricing page, the legal pack and the two hosts.** Build `/owner` gated by the server-verified owner token, showing real metrics only from aggregates: signups, weekly active users, watchlist size, alerts created, alerts delivered and failed, giveaway reminders sent and clicked, games tracked, price points stored, ingestion freshness per source (last successful run and last price age per store), cheapest-known coverage, free to Pro conversion, MRR in EGP and in the visitor currency, AI cost, error rate and notification failure rate, with a dash and a reason instead of a fake zero.
