# First ten build tasks for SIR Access Map (round r54, HQ)

Ready to queue for the free agents. **Build last**, after the other small projects, per `D:/Projects/_SIR/plans/BACKLOG_IDEAS_DECISIONS.md` section 7. Each task is one paragraph; the agent reads the plan `D:/Projects/_SIR/plans/sir-access-map.md` and the competitor study `D:/Projects/_SIR/ops/competitors/sir-access-map.md` first, then does only this task, runs the checks, commits, pushes and ticks the checklist.

1. Monorepo scaffold with tokens, RTL, the health route and CI. Create the monorepo skeleton under `D:/Projects/SIR Access Map` (apps/web, apps/api, packages/core, packages/data, packages/ui, packages/kit, apps/mobile, apps/desktop, docs, scripts) with strict TypeScript, Tailwind v4 tokens, RTL-first styles, an `/api/health` route returning JSON, and a `pnpm verify` script that runs typecheck, lint, tests, build and gitleaks. No UI beyond the health route and a placeholder home page with the five states. Exit check: `pnpm verify` runs and the output was seen green.

2. The product's own Firebase project, the project folder and the `owner-auth` package with negative tests. Verify whether a Firebase project and a GitHub repo named `sir-access-map` already exist; if not, create the Firebase project `sir-access-map` on the free Spark plan and the GitHub repo `sirahmed8/sir-access-map` (private) as the only remote, and create `D:/Projects/SIR Access Map` with `.sir/CHECKPOINT.md` and `AGENTS.md` pointing at the plan. Implement `owner-auth` (Google sign-in via Firebase Auth, ID token verified on the server with JWKS, allow-list for owner and admin, HttpOnly Secure SameSite=Strict cookie, rate limits, second factor offer) with negative tests: forged token returns 403, client-side flag flip grants nothing, non-owner token on `/owner` returns 403. Exit check: the tests pass and the Firebase project and repo names are written in the project checkpoint.

3. The data model and the Firestore rules, with emulator tests. Implement the domain types and zod schemas in `packages/core` (Place, PlaceCategory, FeatureKey, FeatureClaim, PhotoEvidence, Confirmation, Claim, RoutePlan, SavedPlace, ModerationItem, User) and the Firestore repositories in `packages/data`, one interface per entity, with deny-by-default rules and per-user and per-place-owner claims. Emulator tests must include a cross-tenant read that fails and a place-owner read of another owner's place that fails. Exit check: the emulator rules tests pass, including both negative reads.

4. The map view with search, category filter and "near me". Implement the map screen on the map provider decided in `docs/DATA_SOURCES.md` (OpenStreetMap/OSRM fallback allowed), with place markers for published places only, search by name, category chips, a "near me" action using geolocation, and the five states. Exit check: the map renders real published places only, an unpublished place never appears, an empty city shows the empty state with one action, and the screen is verified at 390 px and 1280 px in Arabic and English, light and dark.

5. The place profile with the feature checklist, dates and badges. Implement the place detail screen: name, category, address, the feature checklist grouped by entrance, interior, toilet, parking and help, each feature showing its state, verified-on date, photo count and confirmation count, the "reported, unconfirmed" and "needs re-check" badges, the report-a-place and report-a-feature flows, and save-to-saved-places. Exit check: the profile shows every feature with its date and counts at 390 px and 1280 px in Arabic and English, light and dark, with the five states.

6. The submission flow with the feature checklist and note. Implement the submit flow for a new place or a new feature claim: name, category, coordinates (drop pin or GPS), the feature checklist with per-feature state and note, and idempotent creation through a Firestore transaction. Exit check: a submission creates a `reported, unconfirmed` record that never shows as a confirmed feature, 20 parallel submissions are handled with idempotency keys, and the flow is verified at 390 px in Arabic and English.

7. Photo upload with checks, signed URLs and the moderation queue. Implement photo upload for feature claims: size and type checks before upload, signed-URL storage, and the moderator queue view that shows every new place, claim, photo and stale feature with its evidence (photos, confirmations, proof) in one screen. Exit check: a wrong-type or too-large photo is refused, a stored photo is reachable only with a valid signed URL, and the moderation queue resolves an item end to end in a test.

8. The confirmation flow and the publish rules engine. Implement the confirmation flow (a second distinct user confirms or disputes a place or feature claim, one confirmation per user per claim) and the publish-rules engine from plan section 5.3: a place publishes only with a confirmed or owner-verified feature claim, `verified_on` and `recheck_after` are set on confirmation, and stale features get the "needs re-check" badge. Exit check: 20 parallel confirmations produce exactly one confirmed state, a single report stays "reported, unconfirmed", and a feature past `recheck_after` shows the badge and appears in the staleness count.

9. The place-owner claim flow with proof types. Implement the claim flow: a user claims a place, chooses a proof type (document, callback to a listed business number, domain), uploads the proof, and a moderator verifies or rejects it; the claimant console shows claimed places, pending corrections and verification status, and a verified claim marks its feature claims as `owner_verified`. Exit check: a claim cannot be verified without proof (e2e blocked), a place owner sees only their own places (emulator test), and a verified claim updates the place profile badge.

10. The owner-only analytics page and the billing fallback page. Implement `/owner` with server-verified owner token and 403 for everyone else, showing real metrics only (users, published places, pending moderation items, claims pending verification, confirmations per day, photos uploaded, route plans created, staleness count, AI cost, error rate, subscriptions, revenue), the place-owner section scoped to the owner's own places, and the pricing page with the test prices from plan section 7, auto-detected currency, "Subscriptions launching soon" and an email capture that creates a lead document and rejects an invalid address. Exit check: a non-owner token on `/owner` gets 403, a forged token gets 403, the pricing page shows the test prices with auto-detected currency, and the email capture creates a lead document and rejects an invalid address.
