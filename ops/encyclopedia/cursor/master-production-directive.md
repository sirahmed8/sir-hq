## When to use / when NOT
Use when starting or auditing any product build in the SIR ecosystem — it is the standing quality contract. Not a task procedure for a single bug fix; invoke its audit checklist proportionally.

## Inputs, outputs, tools
- Inputs: a project (greenfield or existing) plus its stack.
- Outputs: code + UI meeting the 15-section bar; a continuation checkpoint file.
- Tools: whatever the project uses; references sibling skills (legal-compliance-shield, high-conversion-copywriting, etc.).

## 5 most important rules
1. Zero placeholders, zero fake/mock data, zero broken imports, zero AI slop — non-negotiable floor.
2. Every view implements all 5 states; every interactive element gives <400ms feedback and does something real.
3. Security floor: HttpOnly cookies, server-side authz, rate limits, parameterized queries — the "5 fatal flaws" are banned patterns.
4. Payment unconfigured = graceful disabled "Coming Soon" state with lead capture, never broken checkout.
5. Finish with the Phase-4 self-audit (responsive, contrast, RTL, stepper causality, fallback, owner bypass, security, legal) and update the checkpoint.

This directive mandates owner-specific monetization (EGP) and owner-OP-mode patterns — applying it to non-owner products needs adaptation. Some sections (multi-agent orchestration, council) are aspirational process, not code. It is long; apply proportionally rather than literally for small tasks.
