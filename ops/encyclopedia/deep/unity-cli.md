# unity-cli (gemini-plugin: unity)

## Summary
unity-cli is the foundational Unity skill: everything about driving Unity through the `unity` CLI instead of clicking the Editor. It teaches "search, don't grep help" — `unity commands --grep <word>` or `unity command --query <name>` discover command schemas at runtime, because the catalog differs per Editor/Pipeline version. Covers: editor detection (`unity status --until-ready`, `unity editors running`, `--project-path` when multiple Editors are open, `script eval` caveats — statement block only, no usings, fully qualified types), install/onboarding (check `unity auth status`, install editors with `unity editors install --stream lts`, template ids must be queried not guessed — `com.unity.template.urp-blank` for 3D, `com.unity.template.universal-2d` for 2D, Built-in templates deprecated from 6.5), the bootstrap order (install Pipeline package BEFORE first open, then `unity open`, `unity status --until-ready`), git/UVCS project init with `.gitignore` download and LFS guidance, and references/ has 13 docs: auth-license-cloud, build-run-test, cloud-automation, collaboration, config-hub, diagnostics-maintenance, docs-workflow, editors-install, integration-advanced, playmode-verification-loop, projects-templates, version-control.

## When to use / when NOT
Use for ANY Unity automation work: installing/editors, creating projects, opening/editing scenes or assets, builds, cloud builds, tests. Do NOT use it for package management specifics (unity-package-management), URP rendering (urp-postprocessing), or sprite sprite workflows (sprite-editor) — those skills layer on top and defer to this one for editor access.

## Inputs, outputs, tools
- Inputs: user request + `unity` CLI commands with `--project-path`, `--format json`, `--until-ready` flags.
- Outputs: command results (JSON), Editor state changes, generated projects.
- Tools: the `unity` CLI binary (install via official installer; verify with `unity --version`), shell. 13 reference docs for depth.

## 5 most important rules
1. ALWAYS `unity status` first before driving an Editor; pass `--project-path` when more than one is open — a bare command may hit the wrong Editor.
2. Never guess command parameters — query the schema (`unity command --query`) because it is generated by the Editor's Pipeline package version.
3. `script eval` is a statement block: no `using` directives (CS0210), all types fully qualified (CS0246/CS0104), returns a value; check `script eval_file` availability separately.
4. Install `com.unity.pipeline` into Packages/manifest.json BEFORE first Editor open, or `unity command`/`status` won't exist.
5. Pick editor stream deliberately: LTS for shipping, tech only for unreleased features, beta/alpha evaluation-only; pick templates by RENDER PIPELINE (universal-2d/urp-blank), not just 2D/3D.

## Risks / things needing the owner
Requires `unity` CLI installed and signed in/licensed (`unity auth status`); auth/license problems are owner-only (sign-in, license acceptance). Editor installs are large downloads. Cloud builds need Unity Cloud credentials. `unity run` injects `-quit` which breaks async UPM installs — unity-package-management documents the workaround. Nothing else needs the owner.
