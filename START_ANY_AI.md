## 3. Quality bar (weak or old models fail here: read twice)
Follow `_SIR/standard/23-premium-code-bar.md`. Always clean code and clean architecture: layered (presentation, domain, data, core), files under 300 lines, strict types, tests next to logic, no dead code, no duplicated logic (extract), no god components, clear names, absolute imports. Premium UI: current stable stack, design tokens, themes (light, dark, system, high contrast), RTL-first Arabic + English, spring motion, five states per screen, real design (never a plain template page), nothing hard-coded that belongs to the user, no fake numbers or users, no hype words or emoji headers, security by default. Proof before "done": type check, lint, tests, the project's verify script, screenshots for UI.

## 4. Plans and tasks (every project, every time)
After analysing a project write a better PLAN.md, ARCHITECTURE.md, DESIGN.md, QUALITY.md, PRODUCTION.md, PLATFORMS.md, BENCHMARK.md and a task list with acceptance tests, based on what the best products in that category do (web research) and on the real code. Re-plan whenever you learn something. Every gap becomes a task; every task has evidence when ticked.

## 5. Never run out of work: find bugs three ways
1. Look: screenshots of the app, site and every platform that exists (web at 390 px and 1280 px in LTR and RTL, dark and light, installed PWA, Android via ADB, Windows window) using the browser and computer-use tools; batch actions, few shots, compare with DESIGN.md.
2. Read: analyse the code like a reviewer; ask "what input, state or timing makes this break?"; trace flows end to end (auth, relay, offline, empty data, slow network, big lists, RTL), read logs and `git log` for repeated fixes, run linters, type checks, dependency and secret audits, Lighthouse and accessibility checks.
3. Break: write tests for every bug found (fails first, then fix), fuzz inputs, kill services and watch recovery.
When the list is empty, do this again, then improve performance, polish, docs and tests. The loop ends only when the owner says stop.

## 10. Usage limits: never get cut off mid-change
- Check usage often (your app's usage command, or the 5-hour and weekly meters). At about 80% weekly or when a 5-hour window is nearly full, stop starting new work and enter wrap-up mode; at 90% finish what is in flight only.
- Wrap-up mode: finish or shelve the current step so the tree is green (run the verify script); anything half-done goes behind a flag or into a clearly marked unticked task with exact files, never into main in a broken state; commit small, push to main only when verify is green; deploy only verified work (rules before site, rollback ready, health check after: doctor, /health, site 200); write `.sir/CHECKPOINT.md` with the exact Next step and commands so the next AI (any app) continues at once; update the Control Room and tell the manager/HQ in the bus file; stop sub-agents cleanly (tell each to commit its own files and report).
- If a rate-limit error already hit: do not retry in a loop. Save state (checkpoint, commit what is green, `git stash` nothing important away), record which agent was mid-task with its id and what it still owes, and stop. Another worker or the same one after the reset resumes from the checkpoint.
- Prefer cheap models, small contexts and scripts for routine work so the quota lasts; keep the strongest model for design, review and security.

## 11. The daily company rhythm (CEO model)
- Ahmed is the CEO. The manager (Claude) owns the roadmap under him: every day it creates new tasks and drives workers. No project is "done" by an agent's opinion: it stays in the rotation until Ahmed says "next project" or "focus here"; he may also report bugs or new ideas at any time, which become top tasks.
- Daily menu for the active project (pick the highest value, always at least three, mix them): UI/UX polish and consistency; new useful features from the BENCHMARK; logic and back-end correctness and speed; front-end performance and accessibility; security hygiene (dependency audit, secret scan, rules review); test coverage on risky code; error handling, empty/offline/slow-network states; docs and in-app help; observability and logs; cleanup and refactors that remove duplication; release notes (generated changelog) and a deploy when verified.
- Weekly: re-plan (PLAN, TASKS, BENCHMARK updated from what was learned), review all open bugs, check platform coverage (web, PWA, Android, Windows, others as planned), disk and machine health, backup and restore drill.
- Waves: the Control Room shows waves of projects and their tasks; every agent updates its project's tasks and plan files when reality changes, then the dashboard (section 8). Plans and tasks are living documents, not a one-time contract.

## 12. Safety net for every change

Deleting files: always to the Recycle Bin or the quarantine folder (restorable); never permanent deletion, never empty the Recycle Bin: Ahmed does that himself. ## 15. Senior full-stack checklist (apply to every project, whether or not it was mentioned)
Product: who is the user, the one job the screen does, onboarding in under a minute, empty/loading/error states, undo instead of confirm, helpful copy, search, keyboard shortcuts, notifications that matter, settings with sane defaults, feedback and support path, analytics only with consent and only what is needed.
UX and design: consistent design system, spacing and type scale, touch targets, focus order, contrast, motion with reduced-motion fallback, dark/light/high contrast, RTL mirroring, responsive from 320 px to 4K, skeletons not spinners, optimistic UI with rollback, offline-first where it fits.
Front end: server vs client components, code splitting, image and font optimisation, caching and revalidation, state kept small and typed, forms with validation and accessible errors, no layout shift, error boundaries, service worker versioning, bundle budgets.
Back end and data: clear API contracts (typed, versioned), validation at every boundary, idempotency keys, pagination (cursor), rate limiting, retries with backoff, timeouts, queues for slow work, transactions, migrations with rollback, indexes, backups with a restore drill, data retention and deletion, encryption at rest for private data, audit logs.
Security: authentication and session hardening, authorisation checked server-side, secrets in a vault not in git, least privilege, dependency and licence audit, CSP and security headers, SSRF and injection defence, file upload checks, abuse and spam controls, threat model per feature, incident runbook.
Quality and ops: unit, integration and end-to-end tests with fixtures, flaky tests fixed not skipped, CI on every push, preview deploys, feature flags, canary and rollback, structured logs, error tracking, health checks, uptime alerts, performance monitoring, cost and quota monitoring, dependency updates on a schedule, a README that works from a clean clone, architecture decision records, onboarding docs for the next engineer or AI.
Delivery: semantic versions and a generated changelog, store/listing assets, signing keys safe, update channel, accessibility and privacy statements true to the code, legal pages from what the product really does.
Craft: small functions, names that explain, one reason to change per module, delete dead code, no copy-paste, comments explain why, types as documentation, consistent errors, boring reliable choices over clever ones, measure before optimising, leave every file cleaner than you found it.

## 16. One global design system (studied, shared, never re-invented)
- Every project has its own look (colors, icon, tone) but they all stand on ONE global system kept in `D:\Projects\SIR Platform` (or `_SIR/standard/05-design-system.md` until the package exists): design tokens (color roles, type scale, spacing 4/8 grid, radii, elevation, blur, motion curves and durations, z-index, breakpoints), themes (light, dark, system, high contrast) and an engine switch if the project has one, plus a shared component library with documented states: buttons (primary, secondary, ghost, destructive, icon, loading, disabled), links, text fields, text areas, selects, checkboxes, radios, toggles, sliders, steppers, tabs and segmented controls, lists and rows, tables, cards, chips and badges, dialogs, sheets, drawers, menus and popovers, tooltips, toasts, progress and skeletons, empty and error states, avatars, navigation (tab bar, sidebar, app bar), forms, charts. Each has variants, sizes, states (hover, focus, active, disabled, loading, error), RTL behaviour, motion and accessibility rules (focus ring, labels, 44 px targets).
- Studied, not guessed: before building a screen, study the best products in the category and the platform guidelines (Apple HIG, Material 3, Fluent, WCAG 2.2), then write down the pattern (when to use which component, spacing, copy tone). Keep the studies in `DESIGN.md` per project and the shared rules in the global file. A new project starts by importing the global tokens and components, then sets only its brand tokens (primary color, icon, radius feel, font pair).
- Rule: never create a new button, input, card or toggle inside a feature. Use the global component; if it is missing or wrong, improve the global component first (with tests and a visual story/screenshot), then every project benefits. One change in the system updates all products; each project keeps a thin theme file. Detect drift: grep for ad-hoc styles, hard-coded colors, px values and copy-pasted components, and migrate them.
- Maintain a living gallery (a storybook-style page or route) per project that renders every component in every state, theme and direction, used for visual checks and screenshots.
- Keep expanding: add components and patterns as products need them (data tables with sorting and virtualisation, date and time pickers, command palette, file uploader, media player, chat bubbles, onboarding flows, notification center, settings layouts), and tell every project to adopt the improvement.
